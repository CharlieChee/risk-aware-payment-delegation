\section{Essential Controls, Robustness, and Reuse}
\label{app:execution}
\subsection{Prompt Engineering and Executable Decisions}
\label{app:prompt-controls}
We test whether additional textual reasoning and verification guidance can substitute for executable decision processing. Our \emph{prompt engineering baseline}, abbreviated \emph{Prompt}, appends a generic checklist to the original Direct instruction: identify requirements, check all applicable conditions, verify financial arithmetic and boundaries, compare eligible purchases, and review the final decision. Direct already specifies joint feasibility, worst-case utility, and justified refusal. Thus Prompt tests additional guidance within the same decision policy; neither Direct nor the executable framework is prompt-free.

\paragraph{Controlled inputs.}
We complete 200 new calls for each of DeepSeek low/high and Sol/Luna/Terra medium. For each Direct--Prompt pair, the recorded task, catalogue, answer schema, model, requested reasoning setting, output-budget configuration, and deadline are unchanged. The appended checklist contains no task-specific examples or reference answers. Both routes return a decision without external execution or further user interaction. DeepSeek uses the original checklist; the native-model version retains its five checks but removes the additional prohibition on internal program-like representations. The comparisons use retained Direct runs, so service-version drift across run dates is not controlled. The two checklist versions are documented with the released prompts, rather than treated as a separate version ablation.

\paragraph{Effect of textual guidance.}
Table~\ref{tab:prompt-control} shows lower exactness in four configurations and a one-percentage-point increase for Terra. The observed changes range from $-6.5$ to $+1.0$ percentage points. This generic prompt engineering intervention does not yield a consistent improvement; the result concerns the tested checklist, not the effectiveness of prompt engineering in general.

\paragraph{Four-method comparison.}
Table~\ref{tab:four-way-controls} compares Direct, Prompt, Framework + Set, and Framework + Python on identical tasks within each row. The latter two generate executable representations under the same outer admissibility, worst-value, and selection policy. Set compiles without the catalogue, whereas the other three routes receive it; this comparison evaluates complete realizations rather than isolating syntax alone. DeepSeek has all 200 tasks for every method. For Sol, Luna, and Terra, the earlier Python control shares 40 primary tasks: one feasible/infeasible pair per template, selected for that earlier panel independently of outcomes. We verify that their task attributes and reference decisions agree with the primary versions. These paired controls use retained per-trial runs, separately from later aggregate primary updates.

\subsection{Execution Controls: Risk and Useful Completion}
\label{app:execution-controls}
The procedural control generates a Python \texttt{assess(attrs)} function under the same outer admissibility, worst-value, and selection policy as Set. It is a program-aided control, not an exact reproduction of PAL or Logic.py. Primary and effort controls receive the catalogue; the matched-input control and Set compile without it. Table~\ref{tab:execution-ablation} reports risk, useful completion, and exactness for the primary DeepSeek comparison, all completed effort groups, and the identical-input control.

\begin{table*}[!tbp]
\centering\footnotesize\setlength{\tabcolsep}{4pt}
\input{tables/execution_controls}

Matched-input controls use low/high/max, with 72 tasks per setting. Cohorts and reused Set results are not pooled across groups.}
\label{tab:execution-ablation}
\label{tab:authorization}

In the two primary DeepSeek configurations, both realizations complete 186/200 feasible outcomes, while State-wise records nine unsafe acceptances versus eighteen for the procedural control across 400 outcomes per method. The unsafe-rate difference is $-2.25$ percentage points (95\% template-bootstrap interval $[-6.75,+0.75]$). This is a cohort-specific observation: procedural exactness matches or exceeds State-wise in several other groups. The control therefore separates risk, completion, and exactness rather than treating any one metric as sufficient. Systematic representation optimization is left to separate work.

\subsection{Task language}
\label{app:language}
The original study uses the same 60 identifiers for four profiles, two languages, and three methods: 1,440 outcomes. A reviewed 183-phrase map preserves identifiers, quantities, types, events, and authorization; system-level method instructions stay fixed. Table~\ref{tab:language} gives Direct/Set results on the 60-task panel and a separate 200-task Astra panel. The two panels have different task counts and are reported separately.

\subsection{Output-budget control}
\label{app:budget}
The Direct budget control pairs original output caps with a 262,144-token cap on 46 historically budget-sensitive tasks, yielding 92 new calls. Each pair uses the same 1,800-second deadline and differs only in output cap. Exact decisions increase from 10/46 to 26/46 (Table~\ref{tab:budget}). These new attempts do not overwrite first outcomes.
